# 収納代行会社の選定（口座振替の裏側をどこに借りるか）

CarePAY は「金融屋」ではなく現場専用の請求OS。口座振替（収納代行）は**自社で持たず、既存会社の裏側を業態で使い分ける**方針。本書はその選定軸と候補比較。

最終更新：2026-05-29

---

## 結論（推奨スタンス）

1. **立ち上げ期は1社に寄せる**。多接続は事務とリスク管理が重くなる。まず医療・介護で実績のある収納代行を主軸に。
2. **主軸候補：アプラス（新生銀行グループ）または三菱UFJファクター系**。金融機関カバレッジ・与信・医療介護の導入実績で安定。
3. **小口・スモールスタート併用：月額パンダ / サブスクペイ**。初期費用・最低件数のハードルが低く、小規模施設のオンボーディングに向く。
4. **カード自動課金は Square 一本**（口振開始までの立替・未収再請求の即日導線）。口振とカードは役割分担。

---

## 選定軸（医療・介護・福祉に効くもの）

- **金融機関カバレッジ**：地銀・信金・ゆうちょまで広く対応できるか（高齢者の口座はゆうちょ・地銀比率が高い）。
- **Web口座振替受付**：通帳・銀行印なしでオンライン登録が完結するか（市場標準。無いと候補外）。
- **初期費用・月額・1件あたり手数料**：小規模施設でも乗せられる価格か。
- **最低利用件数・審査期間**：スモールスタート可否。審査が長いと現場が止まる。
- **入金サイクル**：振替日から事業者入金までの日数（資金繰りに直結）。
- **再振替・未収データの返却形式**：CarePAY の債権管理へ取り込める CSV/API があるか。
- **API/データ連携**：手作業の請求データ授受でなく、ファイル or API で自動化できるか。
- **医療・介護の導入実績**：レセプト周辺・施設利用料の収納実績。

## 候補比較（一次情報で都度更新すること）

| 会社 | 立ち位置 | 向いている規模 | 着目点 |
|---|---|---|---|
| アプラス（SBI新生銀行G） | 大手収納代行・信販 | 中〜大 | 金融機関カバレッジ広い・実績豊富。価格は要相談 |
| 三菱UFJファクター | 銀行系収納代行 | 中〜大 | 安定・信頼性。導入要件はやや堅め |
| ゼウス | 決済・収納代行 | 中小〜中 | カード含む総合決済。Web完結に対応 |
| DSK（電算システム） | 収納代行 | 中〜大 | コンビニ・口振の総合収納に強い |
| 大阪ガスファイナンス | 収納代行 | 中 | 公共料金系の実績 |
| 月額パンダ | サブスク型収納代行 | 小〜中 | 初期費用低め・小口向け・Web口振 |

> 注：手数料・最低件数・入金サイクルは改定が頻繁。商談前に各社の最新条件を一次情報で確認する。

## 業態別の当てはめ（たたき台）

- **介護施設（特養・老健・介護医療院）**：利用者の口座はゆうちょ・地銀比率が高い → カバレッジ重視で**アプラス/UFJファクター**主軸。
- **クリニック・自費診療**：件数は少なめ・単価バラつき → **月額パンダ/サブスクペイ**で軽く始め、伸びたら主軸へ移行。
- **訪問・通所/障害福祉**：請求が毎月・小口多数 → API連携の軽さ（サブスクペイ等）＋将来カバレッジ移行。

---

## 移行を前提に設計する

CarePAY 側のデータモデル（`backend/migrations/0001_init.sql` の `facilities.collector`）で収納代行をテナント単位に持つ。
**収納代行はいつでも差し替えられる**ように、請求データ授受を CarePAY 標準フォーマット（CSV/API）に正規化し、各社アダプタを薄く実装する。ロックインを避ける。

## 次アクション

1. 主軸候補2社（アプラス・UFJファクター）へ条件照会（手数料・最低件数・入金サイクル・データ返却形式）。
2. 小口併用1社（月額パンダ or サブスクペイ）のサンドボックス検証。
3. CarePAY 収納代行アダプタ I/F（取込CSV・再振替結果・未収返却）の確定。
